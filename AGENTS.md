## Project Context

Caffeinated Whale CLI (`cwcli`) is a command-line tool for managing Frappe/ERPNext Docker instances during local development.
It covers instance lifecycle (init, start, stop, restart, rm), bench and site operations (inspect, run, open, unlock, update, label), and backup/restore including peer-to-peer transfer over sendme.
The source of truth for the user-facing feature set is `README.md`.

## Terminology

Use **instance** as the top-level term throughout.

- **Instance** - one docker-compose deployment (its frappe container, db, redis, named volumes, network).
- **Project** - cwcli's name/identifier for an instance; the compose project label `com.docker.compose.project={name}` and the local config dir `~/.cwcli/projects/{name}/`.
  Code symbols keep the `project_name` / `PROJECTS_DIR` spelling.
- **Bench** - a bench directory inside an instance's frappe container.
  One instance can hold several benches (a **multi-bench** instance).
- **Numeric label** - a bench's index into the stable sorted-by-path order (0, 1, 2, ...).
  It shifts when a bench is added or removed, so it is NOT durable.
- **User label** - a durable per-bench handle stored in the DB and in a marker file inside the bench.
- **Freshness tiers** - `inspect`'s cache strategy: T1 serve cache, T2 partial read-only refresh, T3 full re-cache.
- **Default site** - a bench's default site, read from `common_site_config.json`'s `default_site` OR `sites/currentsite.txt`.
- **Receive-mode** - `restore --receive`, the sendme download-then-restore path (the most destructive path in the codebase).
- **Sendme** - the iroh-based peer-to-peer blob transfer used by `restore --send`/`--receive`.

- **`init` port check skips a project's OWN live ports** (`core/init.py:_project_containers_running`) - re-running init against a RUNNING instance is the ordinary way to add a bench or a site to it (`cwcli init existing --reuse-bench --site other`), and there every port the check finds bound is bound by that very instance. It used to refuse outright and advise `--port`, which cannot be followed: an existing instance's ports are frozen in its compose file. Same self-conflict the `auto_start=True` retry already skipped, reached by the other route, so the skip is now keyed on the project having a running container of its own rather than on the call shape. The check still runs for a STOPPED or absent project, where a bound port genuinely belongs to somebody else, and an unreachable daemon is NOT treated as running (it falls through to the check; the compose calls surface the real failure).

The admin password is generated when `--admin-password` is omitted (interactive only; required non-interactively), used verbatim when supplied, and printed once - gated on `report.site_created`; generation and the TTY gate stay in the frontend. See skill: `cwcli-lifecycle`.

- **`inspect` 3-tier freshness, on the core** (`core/inspect.py`; `commands/inspect.py` is a renderer) - cache-backed with a read-only drift check; escalates to a full re-cache only on real drift. The tier machine AND the cache write live in `core.inspect` (`inspect_raw` serves the human renderer's byte-identical cache-shaped dicts; `inspect` returns the typed, secrets-free `Result[InspectReport]`); the T2 write-never / T3 write-on-success / drift-degrade serve-without-persist contract is ONE contract owned there, not re-implementable per frontend. `cwcli axi inspect` is the agent verb (one tiered read; no `--yes`). `discover_benches`/`partial_refresh` are the public core spellings of the old private helpers. **Per-site `installed_apps_verified` is the fail-honest verified-or-remembered token** (`fm/cwcli-axi-inspect-serves-stale-ref`, mirror of `where`'s `project_state`): only a T3 full inspect re-runs `bench list-apps`, so the cheap T1/T2 tiers carry the cached `installed_apps` (each entry `name version branch`) forward UNVERIFIED, and a `git checkout` inside an app touches neither the `apps/` listing nor the site set T2 watches - so a stale ref rode a `served_from: partial` read looking fresh, the class that once made a downstream test validate the wrong code. The token is True only when `served_from == "full"`; when a non-full read carries a non-empty app list, a `inspect.apps_unverified` warning names `--update`. Note: `installed_apps` is app-REGISTRY metadata from `bench list-apps` (install-time name/version/branch), NOT a live `git rev-parse` - no tier can cheaply re-observe a checkout from that field, which is exactly why the honest token ("or refuses") is the fix, not "always print the live ref"; git stays the authority on the checked-out ref (proven live in `tests/e2e/test_axi_inspect_stale_ref_e2e.py`). **Read-surface audit** (the reporter's scope note, established not assumed): only `inspect` and `where` vouch for evidence-grade REMEMBERED state and both now carry the token; `ls`/`status` read LIVE Docker/`supervisorctl`, `config` reports cache metadata AS metadata, and `benches` serves remembered addressing (paths/labels) but those are validated on USE by the next live op rather than consumed as correctness evidence - the lower-severity, self-correcting case left deliberately untokened.
  See skill: `cwcli-inspect-benches`.
- **Multi-bench addressing** (`utils/bench_labels.py`, `commands/utils.py:resolve_bench_path`) - `--bench <index|label>` selects a bench; a multi-bench operation that acts on one bench requires a selector instead of guessing.
  `status` is the deliberate read-only exception: without a selector it reports every bench.
  Labels persist to BOTH the DB and an in-bench marker file for cache-loss recovery.
  See skill: `cwcli-inspect-benches`.
- **`rm` deletion + backup gate on the core** (`core/rm.py`; `commands/rm.py` is a renderer) - `core.remove(project, *, remove_volumes=True, no_backup=False, on_event) -> Result[RemovalOutcome]` removes named volumes and the project dir that `Container.remove(v=True)` leaves behind, gated by a verified copy-out backup of EVERY bench that fails closed. It also removes the project's OWN compose network by exact `com.docker.compose.project` label (never a prune), regardless of `--no-volumes` since the network holds no user data; a network with an outside endpoint still attached is refused, not forced, and reported via `RemovalOutcome.network_removed` on both the human and `axi` surfaces. See `cwcli-lifecycle` skill's `rm.md`. rm's `_backup_sites` is a copy-out-and-VERIFY gate (streams each artifact out and confirms the DB dump landed non-empty on the host archive), DISTINCT from `core.backup`'s in-container dump - reusing `core.backup` would drop the verification that IS the C1 gate. A STOPPED project on the `--volumes` path is transiently STARTED for that backup (start -> back up -> delete, reusing `start`'s port-conflict handling); if it cannot be started or backed up, rm ABORTS, keeps all data, returns the project to stopped, and exits non-zero (`--no-backup` is the escape hatch; orphans with present or unverified named volumes are refused likewise, while confirmed volume-free orphans need no backup after a cleanup-time recheck). The transient-start orchestration stays FRONTEND (it prompts via `_check_port_conflicts`); `core.remove`'s not-running branch is the fail-closed backstop. The exit code reads `outcome.failures`, NOT `result.status` (the `update` precedent). **`cwcli axi rm` SHIPPED** (`add-axi-rm-verb`, captain-approved 2026-07-21) as a thin TOON renderer over the UNCHANGED `core.remove` (zero `core/rm.py` delta), reversing the deferral. The approval overturned the WHETHER - may an agent hold this capability at all - and **waived no safety property**, so the early fail-closed gate, the verified copy-out and the `outcome.failures` exit code are literally the human verb's code. Two things the agent surface DECIDED rather than inherited, because the human FRONTEND owns them: (1) **`--yes` grants consent ONLY** and never the auto-start the human `--yes` also grants (that fusion is what `migrate-rm-core` kept out of the core; re-creating it would mean an agent asking to DELETE had thereby STARTED - the `axi apps checkout` threat); (2) **NO `--no-backup`**, the C1 gate's off switch, with no named beneficiary here (the `axi apps install` `--force` / `axi migrate` `--skip-maintenance` rulings) - the human verb is the hatch. Consequence: a STOPPED project on the volume path cannot satisfy the gate, so it is refused `NOT_RUNNING` exit 1 BEFORE the core call, scoped to STOPPED (an ORPHAN goes to the core, which alone tells leftover volumes from a project genuinely gone). **Every refusal names its ways out** (`cwcli start`, `--no-volumes`, `cwcli rm --no-backup`) - a destructive verb answering only "no" pushes its caller back to the raw command. ONE project per invocation, never the variadic list or stdin pipe. `tests/test_core_rm.py::TestAxiRmVerbShipped` + `tests/test_axi_rm.py` pin both decided properties; proven end to end in `docs/e2e/axi-rm-destructive-lifecycle.md`. See skill: `cwcli-lifecycle`.
- **`rm-site` drops ONE explicitly named site, never the instance** (`core/rm_site.py`; `commands/rm_site.py` and `commands/axi.py` are renderers) - the required site argument has no default fallback, consent stays in the core, and an archive is pruned from the container only after a verified host copy. - **`restore` on the core, a plan/apply split** (`core/restore.py`; `commands/restore.py` is a renderer; batch 11, `migrate-restore-core`) - cwcli's MOST destructive path, migrated as `restore_plan`/`receive_plan -> restore_apply`: a **read/destroy safety separation** (the batch's headline finding, the destructive-preview boundary the core-rework deferred here). `restore_plan` is the pure, repeatable, secret-free resolve (container/bench/site, scan, selection, missing-apps, origin) returning a `RestorePlan` that DESCRIBES the destructive action; `restore_apply(plan, *, consent=False, ...)` is the single guarded act that ALONE takes the credentials and consent, runs `bench restore --force`, merges the encryption key, and migrates + restarts. It is NOT generator laziness (nothing returns an iterator) and NOT a removal of consent from the core (`restore_apply(consent=False)` returns `NEEDS_CHOICE`/`confirm_restore`, the `apps uninstall`/`config cache clear` lesson: consent must never be a frontend-only decision axi/GUI can bypass). Preserved byte-exactly: the destructive confirm on BOTH normal and receive paths, the non-interactive `--latest`/`--backup-file` selectors, secrets off the argv (M5, buffered `exec_run(environment=)` - the `backup` shape, NOT exec-stream: a buffered exec blocks and returns a real code), the streamed `put_archive`/`get_archive` copies (M4), and post-restore migrate + restart (a failed migrate is a `WARNING` carrying `migrate_ok=False`; the frontend exits 1 on `migrate_ran and not migrate_ok`, the `core.update` report-drives-the-exit-code precedent). The interactive backup menu is a `select_backup` `NEEDS_CHOICE` the CLI renders (the "Restore from remote source" entry is a frontend affordance diverting to receive). Container/bench/site resolution stays a no-spinner frontend PROLOGUE (the `backup` precedent, because every path resolves them BEFORE the scan/download - byte-exact ordering; `_resolve_bench_prologue` collapses the 3 old fallback copies); the core keeps backup-style belt-and-suspenders resolution. The sendme send/receive subprocess + ticket prompt stay frontend (the `commands/logs.py` `-it` precedent: interactive host I/O the core does not consume). Two reported items (zero new primitives otherwise; `select_backup`/`confirm_restore` are new `Choice.kind` tokens): (1) restore keeps its OWN live-`currentsite.txt` default-site resolver, stricter than `resolvers.resolve_default_site`, private to `core/restore.py` (widening the shared one would change `backup`/`unlock`); (2) `--receive` takes `--ticket <sendme-ticket>` for the non-interactive path; a non-TTY without it refuses (exit 1, names `--ticket`) rather than the old silent exit-0 no-op (`commands/restore.py:_run_receive`; the ticket prompt/refuse stays frontend since the sendme subprocess does). There is NO `axi restore` verb - DEFERRED as the captain's own product decision (a `bench restore --force` dropping a live site's DB is the `axi apps uninstall` class of captain-owned deferrals; both `axi init` and `axi apps install` were once in that class and have since SHIPPED on their own approval), asserted against the registry so it can never read as forgotten.

- **Cache never stores secrets** (`utils/db_utils.py`) - a whitelist redaction at the single write chokepoint; nothing reads secrets back from the cache.
  See skill: `cwcli-inspect-benches`.
- **`where` reports verified vs remembered** (`core/where.py`) - the cache OUTLIVES the instances it describes, so a removed project's apps and sites stay in it, and `where` used to serve those rows identically to live ones - including while the Docker daemon was unreachable, the one moment it could have known cheaply that it was guessing.
  A decision was approved on the strength of one such hit.
  Every `WhereMatch` now carries `project_state` (`present`/`absent`/`unverified`) and `WhereResult` carries `verified`, cross-checked against `core.list.list_instances`.
  The per-row token is load-bearing, NOT just the warning: an agent parsing the TOON table must be able to act on the distinction without parsing prose.
  `_live_project_names` fails HONEST, never fail-open - an unreachable daemon returns `None` (everything `unverified`), and must never degrade to an empty set, which would read as "every cached project is gone".
  Verification is ONE Docker project listing per invocation regardless of match count (the same call `axi ls` makes, measured ~75ms against a ~3ms cache read) and never execs into a bench, so it does not re-incur the cost the cache exists to avoid; `verify=False` (`--no-verify`) is the escape hatch and reports `unverified` rather than buying speed by pretending.
  A stale row is REPORTED, never pruned - a read command that silently deleted cached state would be the same defect in the other direction, and refreshing is `cwcli inspect`'s job.
  Pinned by `TestVerifiedVsRemembered` (`tests/test_core_where.py`) and `test_where_never_presents_a_cached_answer_as_verified` (`tests/test_axi.py`).

- **`label` on the core** (`core/label.py`) - split as `list_benches` (the read; a missing selector is a legitimate request, NOT a `NEEDS_CHOICE`) + `set_label`/`clear_label` (two functions, so no `label=None`-means-clear sentinel escapes into the public API). It is the FIRST production caller of `resolvers.resolve_container_state(offer_choice=False)` - a label change must never auto-start a stopped project - which is why that primitive's hardcoded `--yes` hint is now the `not_running_hint` parameter (`label` has no such flag). `clear_label` clears the MARKER before the cache and fails closed on both paths; `set_label` deliberately does NOT check its cache write (asymmetric but self-healing via `inspect`) - see `cwcli-label-setpath-db-check-a3`, and do not tidy it into symmetry. `cwcli axi benches` is the discovery verb that answers every other verb's `--bench`. **`set_labels`** is the batched sibling that backs `inspect -i` (`fm/cwcli-inspect-label-leak-i7`): the frontend PROMPTS and hands the collected `(bench_path, label)` answers to `set_labels`, which owns the SAME validate/uniqueness/marker/cache rule for many benches at once - so `inspect -i` no longer re-implements it, and no live Docker object crosses the boundary (the core fetches the container). It differs from `set_label` in exactly three interactive-only ways: a container unavailable (stopped, gone, or daemon unreachable) degrades to cache-only (one `label.marker_skipped` warning) instead of raising; each assignment reports its own `LabelResult` (a rejected label does not abort the batch); and uniqueness is first-wins WITHIN the batch. It reads/writes the cache once, so it never re-persists a T2 read-only refresh the old bulk write could.
- **`apps` command group** (`commands/apps.py`, `core/apps.py`) - first-class app management (list/install/uninstall/update/checkout) per bench and multi-site by default; `cwcli update` is now a deprecated alias for `apps update`. EVERY subcommand has `--json`, `update` included.
  **`apps checkout <project> <app> <ref> [--reset]`** (`core.checkout_app`) fetches + checks out an arbitrary branch/tag/commit into an app that ALREADY EXISTS in the bench (`apps/<app>`) - the gap install (`bench get-app`, a fresh clone) and update (`bench update --pull`, tracked upstream) leave - so a feature branch can be put under test in the instance the app lives in. It runs `git fetch <remote> <ref>` then `git checkout -B <ref> FETCH_HEAD` (FETCH_HEAD, not `<remote>/<ref>`: refspec-independent + `-B` makes a re-run idempotent) via `exec_stream` with `workdir=apps/<app>`, stopping at the first failed step; `--reset` adds `git reset --hard FETCH_HEAD` for the clean-tree guarantee build/migrate need. The remote is AUTO-DETECTED (`upstream`, then `origin`, then the first remote), NOT hardcoded `origin`: bench's own `get-app` clones with `--origin upstream`, so a bench-installed app's remote is `upstream` (proven on a real bench) - hardcoding `origin` would fail every real bench app. A dir that is not a git checkout raises `NOT_FOUND`/`app.no_checkout`; a DIRTY tree - anything plain `git status --porcelain` reports, untracked files included - raises `CONFLICT`/`app.dirty_tree` before anything is fetched, and `--reset` is the opt-in through it (see `_refuse_dirty_tree` and the `axi apps checkout` entry below). The private-repo fetch rides the SAME `credential_bridge` as install/update (host `gh`/`glab` -> in-container git; raw token never enters the container, inert for public repos). Returns the shared `AppsReport` (one `AppResult` per git step) so the renderer/exit-code/cache-refresh logic is reused verbatim. Built for `frappe-workflow-impl-w4` (Step 3 feature-branch fetch + Step 7 post-merge reset).
  **`cwcli axi apps checkout` SHIPPED** (`add-axi-apps-checkout-verb`, captain-approved 2026-07-20) as a thin TOON renderer over the UNCHANGED `core.checkout_app` (zero `core/` delta): flags `--bench` and `--reset` only, `emit_result(AppsReport)`, exit code from `report.ok`, the `confirm_start`/`select_bench` forks as exit-2 usage errors, and the human verb's recache epilogue reproduced via `cache.recache_project` (a failed recache is a stderr warning, never a non-zero exit - the mutation already landed). It **reverses** the absence assertion that used to sit in `test_axi_apps_list.py`, and the reversal's reasoning is the durable part: that assertion read "`apps checkout` mutates the in-instance checkout, so LIKE install/uninstall it is a HUMAN verb only", which inherited a rationale it was not covered by. The install/uninstall deferral names ONE threat - an agent DESTROYING SITE DATA, because `bench uninstall-app` drops the app's tables (`migrate-apps-core/tasks.md` §7.1, which also pre-authorized a different answer for non-deleting mutations in §7.2) - and a checkout runs `git fetch`/`git checkout -B` inside a source dir: no bench command, no site, no SQL, no table. **"The agent surface is read-only" is NOT a rule this repo follows** and must not be cited as one: FIFTEEN of the twenty-four live `axi` verbs mutate (`backup`, `unlock`, `stop`, `start`, `restart`, `label`, `init`, `setup`, `rm`, `apps update`, `apps checkout`, `apps install`, `migrate`, `run-tests`, `build`), `axi init` provisions a whole instance and `axi apps update` runs schema migrations across live sites. Judge a proposed mutation verb on its own evidence, as `axi init` was. Safety posture, each guard against a NAMED threat: no `--yes`/auto-start (an agent starting containers a user deliberately stopped); the app must already be a git checkout (a typo reading as a no-op or an implicit install); a DIRTY working tree is refused unless `--reset`, as `CONFLICT`/`app.dirty_tree` raised by `core.apps._refuse_dirty_tree` BEFORE any fetch. That guard is **cwcli's own and deliberately STRONGER than git's**, and the history is the durable part: it originally leaned on git alone (`git checkout -B` refuses a checkout that would OVERWRITE a modified file), documented as "a dirty tree fails", and CI on PR #129 proved that false - a dirty file the target ref does not touch rode through at exit 0, so the protection covered only CONFLICTING edits. The captain's ruling (`cwcli-checkout-docs-overstate-guard`) was to **fulfil the promise, not soften the doc**: it is a SAFETY claim a reader acts on by leaving uncommitted work in an app dir, and these checkouts live in a SHARED dev instance, so the work silently carried across a branch switch may not even belong to whoever ran the command. **DIRTY is defined precisely and the definition is load-bearing**: plain `git status --porcelain`, i.e. staged changes, unstaged tracked modifications, AND untracked files. The first cut of this guard passed `--untracked-files=no` on the reasoning that the guard should cover exactly what `--reset` destroys; **the captain REVERSED that and untracked files now refuse** - a new module written but not yet `git add`ed is uncommitted work in the plainest sense, and it is precisely the case where the tool must not decide on the user's behalf that the file is worthless. Do not re-narrow it (`tests/test_core_apps.py::TestCheckoutRefusesADirtyTree::test_the_status_read_is_not_narrowed_to_tracked_files` asserts the flag's absence on the COMMAND for that reason). - **exec-stream contract** (`core/exec_stream.py`) - the ONE way to exec-and-stream. `exec_stream(container, cmd, *, workdir, environment) -> Iterator[ExecEvent]` yields `ExecChunk(stream, text)` then a terminal `ExecDone(exit_code)`. It is PER-EXEC, not per-verb (`run` has one exec per resolve; `update` has 13 and `init` 10, with logic between them). It owns four things, each guarding a real bug: (1) **the honest exit code** - `exec_inspect` returns `{"ExitCode": None, "Running": True}` while an exec runs, so the key is PRESENT and `.get("ExitCode", 1)`'s default is DEAD CODE; `None` then flowed to success (`run` raised `typer.Exit(code=None)` -> exit 0; `apps` did `or 0`), and since `CancellableStream` swallows `ProtocolError`/`OSError` into `StopIteration` a DROPPED CONNECTION looks identical to a clean EOF - so a destructive `uninstall-app` reported `"ok": True` for an uninstall that may never have run. The code is polled (bounded, so a lost stream cannot hang as `update`'s old unbounded loop did), `ExecDone.exit_code` is typed `int` so the fail-open is unrepresentable, and a genuinely unknown code RAISES `DOCKER` rather than guessing 0 or 1. (2) **the stream tag** - always `demux=True`; `init` routes stderr to `sys.stderr` and axi needs stdout purity. Equivalent to `demux=False` because docker-py builds the same `frames_iter` in both modes and differs only in the per-frame wrapper. (3) **the decode**, via `core/docker.py:utf8_stream_decoder` (moved there from `utils/docker_utils.py` to keep the core off that UI module - see the UI-pure core entry), ONE DECODER PER STREAM (Docker frames at 32KB, `bench` block-buffers at 8KB, so boundaries land mid-character on Frappe's routine unicode `✓ → ─ ⚠`; per-chunk decoding CRASHES strict or corrupts to U+FFFD). (4) **closing the stream** - docker-py documents closing as the caller's responsibility and no consumer did it. Consumers pick a consumption mode: render each event, drain and discard (non-verbose `update`, under a spinner), or drain and join (`apps --json`, stdout purity). Guarded by `tests/test_core_exec_stream.py` + `tests/test_exec_stream_decode.py`. Every streaming consumer is now on it: `init` was the last (batch 9, `migrate-init-core` - its 10 provisioning execs, secrets riding `environment=`), so `utf8_stream_decoder`'s only consumer is the contract itself. `logs` is MIGRATED (batch 6, `core/logs.py`) but is a deliberate NON-consumer of this contract, and that non-consumption is now MEASURED not asserted (`openspec/changes/migrate-logs-core/design.md` Decision 1): its `--follow` is a `docker exec -it` TTY passthrough (`subprocess.run`, the tail stays in the frontend), because re-pointing it onto `exec_stream` was probed against real Docker and leaks an orphan `tail -F` per Ctrl+C (accumulating; Docker has no kill-exec API and closing the socket does not kill the exec'd process), then raises `exec.stream_lost` after ~10s on every routine stop (`_poll_exit_code` sees `Running: True`), and would need `tty=True` which is mutually exclusive with the locked `demux=True` stream tag. The `-it` path it keeps is verified clean (exit 130, zero orphans under a pty). Decision 4 is refined, not stretched: it governs ops CWCLI streams, and `logs`'s bytes never enter the Python process. The bounded `core.read_logs` (`tail -n N`, no follow) that backs `cwcli axi logs` SHIPPED (`add-axi-logs-verb`) and is deliberately NOT on this contract: a bounded read blocks to completion and returns finite output, so it is ONE buffered `container.exec_run` (the `core.backup` shape), not an event stream - `exec_stream` would be the primitive only for a future STREAMING `tail -n N`. `logs` reached the SAME fail-open by its own route (a discarded `returncode`), fixed at its own mechanism by PR #83 and preserved through the migration. See skill: `cwcli-lifecycle`.
- **Console FAST-tier probe** (`core/supervision.py:fused_probe`) - the phase-one foundation, now WIRED as `core.status(..., fused=True)` and consumed by `cwcli serve` (see the next entry). The real-bench median fell from 704ms for `core.status(probe_web=True)` to 192ms for the fused single-exec read, below the approved ~250ms target. The function docstring owns its detailed contract. `status(fused=True)` is an EXEC-BUDGET option only, defaulting False so every existing caller is byte-unchanged: the report shape and tokens are identical, and an UNSUPERVISED bench DELEGATES to the full `_bench_status` per bench, because the marker read (never-started `online` vs supervisor-died `degraded`) and the honcho fallback are honesty properties the fused script cannot give - so the exec budget yields to them, not the other way round. The cost lands only OFF the supervised steady state.
- **`cwcli serve` - the streaming Console daemon** (`core/fleet.py` is the UI-pure model; `commands/serve.py` is the HTTP/SSE frontend; Console phase 2 of 4, phase 3 is the UI). A FOREGROUND command, no auto-start/service/boot-unit, stdlib only (`ThreadingHTTPServer` + `queue` + `threading`) over the already-declared `docker` dep - a THIRD frontend beside the human CLI and `axi`, needing zero new core primitives (the design of record is the de-risk spike, reproduced in `docs/e2e/serve-daemon.md`). Endpoints, all reads: `/api/snapshot`, `/api/events` (SSE, one `snapshot` frame then `delta` frames tagged `tier: instant|fast`, `: keepalive` every 15s idle), `/api/instance/<p>/detail`, `/` (throwaway test page). Three tiers, each answering what the others CANNOT: **INSTANT** is Docker's event stream (one thread, no polling, ~1ms) and answers container up/down ONLY - a lifecycle event moves an instance to `unknown` health, NEVER a healthy token, because a container is up SECONDS before its bench serves (measured 6.6s in the spike, and the browser saw `start(frappe) -> unknown` 114ms before `docker start` even returned); **FAST** polls every RUNNING instance through `status(fused=True)` and is the ONLY tier that sees a supervisord program restart, for which Docker emits no event at all (measured: 3 fast deltas, 0 instant); **LAZY** is `core.inspect` on demand behind the detail endpoint, carrying its own `served_from`/`installed_apps_verified` labels through unchanged. Four rules are load-bearing, each pinned by a test: (1) **`health_key()` diffs STABLE fields only** - it is a reviewed, tested function, never a detail in the loop, because ONE volatile field (probe duration, `uptime_s`, `cpu_pct`, `rss_kb`, a timestamp) inside it publishes a delta per tick forever (the spike found exactly that with `probe_ms` in the payload: 8 deltas in 8 steady cycles); `pid` IS stable and IS included, since a process that died and restarted between two probes reads `RUNNING` both times and the pid is the only evidence. (2) **Event-stream loss RE-BOOTSTRAPS the whole model, never `since=`** - Docker's event buffer is a fixed 256-entry ring that this daemon's own probe exec traffic flushes in ~51s, so a gap replay looks correct and silently returns nothing; the same `event` filter ALSO returns an empty set for any historical query, so history is doubly unusable. Proven against real Docker with a gated reconnect (`docs/e2e/serve-daemon.md` §5). (3) **Unknown is a state, not a default** - never-probed is `unknown`, a failed probe is `unknown` + `probe_error`, an unreadable port stays `web_port: null`, and the instance-level `web_probed` is what tells a reader whether a null `web_http_code` means "unreachable" or "never asked". A probe that finds the container GONE re-bootstraps instead of adopting `offline` over the model's container facts - that combination published `container_running: true` beside `overall: offline`, two fields contradicting each other in one document (found live, fixed, pinned by `TestProbeAndModelStayConsistent`). (4) **Web-probe cadence is decision B** - process health polls every instance on the normal cadence; the HTTP check (one line per cycle in a log a developer reads, 28,800/bench/day at 3s) runs ONLY after a lifecycle event and while a client has that instance open, signalled by `?focus=<project>` ON THE SSE CONNECTION ITSELF, so a closed tab retracts focus with no heartbeat, no timeout, and no extra endpoint. **Binds `0.0.0.0` by default** because the primary environment is WSL and a Windows browser cannot reach a WSL-only loopback listener; measured, `0.0.0.0` is the only bind serving BOTH the `localhost` (WSL forwarding) and WSL-IP routes, and the banner prints the reachable address from a UDP `connect` to TEST-NET-1 (sends nothing; resolving the hostname answers `127.0.1.1` here and is useless). `--host 127.0.0.1` is the restrict-to-this-machine escape hatch. CI runs `tests/e2e/test_serve_e2e.py`; the Windows-browser boundary and the induced reconnect stay in `docs/e2e/serve-daemon.md` because neither is reachable from a Linux runner.
- **`stop --bench` stops ONE bench's stack** (`core/stop.py:stop_bench`; `commands/stop.py` and `axi stop --bench` are renderers) - a DIFFERENT operation from `core.stop`, not a narrowed one: an instance is one container holding sibling benches, so there is no container to stop for a single bench. It reuses `supervision.stop_supervisor` (the same PID-keyed SIGTERM-then-wait `core.start`'s relaunch uses - promote/reuse, never a second teardown) and then `supervision.clear_marker`, because the marker is what distinguishes "started, supervisor died" (`degraded`) from "never started" (`online`): leaving it behind would make a DELIBERATE stop report a permanently `degraded` instance with nothing wrong, which is the same crying-wolf defect as the 404 above, one entry up. `stopped_processes` is DEDUPLICATED (discovery is per-PID and one program can hold several live processes). Multi-bench with no selector returns `NEEDS_CHOICE` `select_bench` for a GUI/other caller, but BOTH shipped frontends always pass a value, so neither prompts - and `stop` with no `--bench` keeps its unambiguous project-wide meaning. It existed because every other bench-scoped verb (`start`, `status`, `restart --process`, `logs`) took `--bench` and this one did not, so taking one bench down meant `docker exec ... supervisorctl` - the escape hatch the agent surface exists to close.
- **`resolve_host_web_url` - the ONE answer to "what address is this bench on"** (`core/resolvers.py`; consumed by `core.open_plan`'s `LaunchTarget.web_url` and `commands/init.py`'s success banner) - TWO hops, and skipping either was the shipped defect: the CONTAINER port from `resolve_assigned_ports(..., fill_defaults=False)`, then the HOST port from the container's OWN live port bindings (`container.ports`). The banner hardcoded `http://{site}:8000`, printing a container port as a host port - wrong under any `--port` base AND wrong for every bench past the first (bench 1 is 8001 inside, 21001 outside on a `--port 21000` instance). Docker's binding table is used deliberately INSTEAD of re-parsing the compose file: it IS the published mapping, so there is nothing that can drift and no second parser (`core/scale.py`'s `_parse_published_range` stays private to scale, which must REWRITE that file). Unresolvable is None and the line is OMITTED - never a guessed port in text a user is meant to click.
- **`scale` - widen the published port range** (`core/scale.py`; `commands/scale.py` + `axi scale` are renderers) - an instance publishes a FIXED range of 6 web (`8000-8005`) + 6 socketio (`9000-9005`) ports cwcli writes at init; per-bench ports are assigned by **bench's OWN `make_ports`** (scans sibling benches in the shared `/workspace` parent, counts up from 8000/9000) into each bench's `sites/common_site_config.json`. cwcli writes ZERO port config (only mirrors ports as DERIVED cache data), so a 7th bench binds `:8006` INSIDE the container but is SILENTLY host-unreachable (no crash, no warning) - the defect `scale` fixes (verified real-instance, `fm/multibench-scale-verify`). Four load-bearing invariants, each a real safety property: (1) **read bench config as the port TRUTH** (`resolvers.resolve_assigned_ports` reads `common_site_config.json` live); NEVER invent a second authoritative port store that can drift from bench's. Reconcile the published range to cover `[8000..max(webserver_port)]`/`[9000..max(socketio_port)]` (and an optional `--to N` floor), preserving the host base cwcli chose at init; it only ever EXPANDS, so re-running when the range already covers is a safe idempotent no-op. (2) **`--no-deps` is MANDATORY** - apply the widened `conf/docker-compose.yml` with `docker compose -p {p} -f docker-compose.yml up -d --no-deps frappe`, which recreates ONLY frappe and leaves MariaDB/Redis + the DB volume untouched (proven DB-safe). NEVER `docker compose down`, never recreate without `--no-deps` - either DESTROYS the database. This is a NEW capability: `core.start` uses the SDK `container.start()`, which cannot change a port mapping. (3) **post-recreation toolchain repair** - recreation reverts `/home/frappe` to the image, wiping the RUNTIME-installed nvm node + pyenv python of v13/v14 benches (v15/v16 are image-baked and survive); `scale` probes each bench's `env/bin/python` and re-runs cwcli's OWN idempotent `_install_pyenv_python`/`_install_nvm_node` (with a `chown_home` align first) ONLY for a genuinely broken interpreter (fail-honest). (4) **consent is a CORE decision** - expanding restarts EVERY serving bench in the instance (they share one container's supervisord; unavoidable, the port map is a container-creation property), so `scale(consent=False)` returns `NEEDS_CHOICE` `confirm_scale` when expansion is needed rather than letting axi/GUI bypass the warning (the `apps uninstall` lesson); a no-op needs no consent. Human `--yes` prompts; `axi scale` renders `confirm_scale` as an exit-2 usage error naming `--yes`. Reports the new host port map per bench; surfaces that MEMORY (not ports) is the real ceiling past a few serving benches. Proven end to end (DB survives via H4 marker, MariaDB container unchanged, frappe recreated, newly-covered ports published) in `tests/e2e/test_scale_e2e.py`. See skill: `cwcli-lifecycle`.

## Conventions

- **Tooling.** Use `uv` (`uv sync --frozen --all-extras`, `uv run ...`).
  Format with black and lint with ruff, both at line-length 100 and scoped to `src/` (`uv run black --check src/`, `uv run ruff check src/`).
  `black` is a **dev-only** dependency (in the `dev` extra, NOT runtime `dependencies`): it is a formatter, never imported or subprocessed by `src/`, so keeping it out of runtime deps keeps the `uv tool install`/`uvx` environment lean - do not move it back.
- **Distribution.** cwcli is distributed as a uv tool: `uv tool install caffeinated-whale-cli` (unpinned, so `uv tool upgrade` works) or `uvx --from caffeinated-whale-cli cwcli ...`.
  Both `cwcli` and `caffeinated-whale-cli` console scripts point at `caffeinated_whale_cli.main:cli`; the `--from` is needed because the command name differs from the package name.
  Install/run/upgrade docs live in `README.md`; the isolated E2E evidence is `docs/e2e/uv-tool-distribution.md`.
- **Exit codes.** A step the tool itself reports as failed must NEVER exit 0: the exit code is the only failure signal automation has, and an agent-facing CLI that pins it to 0 cannot be driven safely.
  Every frontend that aggregates per-step results reads its own report (`report.ok`, `outcome.failures`, `migrate_ok`), NEVER `result.status` - a partial fan-out failure is a `WARNING`-shaped envelope and every other verb maps `WARNING` to exit 0, so reading the envelope reports success for a half-finished mutation.
  `tests/test_exit_codes_on_failure.py` is the cross-surface pin (both the failure and its success twin, since a change that makes everything fail is not a fix); the per-command pins live in `test_apps_characterization.py` and `test_core_run.py`.
  The standing hazard: `typer.Exit` subclasses `RuntimeError`, hence `Exception`, so any broad `except Exception` around a call that raises it silently converts a failure into exit 0 - the frontend handlers that wrap such calls re-raise `typer.Exit` explicitly before their broad branch, and a new one must do the same.
- **Types.** Keep `uv run mypy src/` at zero errors; it is a blocking gate.
  Prefer accurate annotations over `# type: ignore` (there are none in `src/`), and add the matching `types-*` stub (`types-requests`, `types-toml` are dev deps) rather than ignoring an untyped import.
  Do not loosen `[tool.mypy]` to hide errors.
- **Tests.** Two tiers, split by marker (registered in `pyproject.toml`; `tests/conftest.py` auto-applies `unit` to anything not marked `e2e`/`e2e_p2p`/`e2e_pkg`).
  A bare `uv run pytest` runs only the fast `unit` tier (no Docker; the default `-m "not e2e and not e2e_p2p and not e2e_pkg"`); the real-Docker tier is `uv run pytest tests/e2e -m e2e` (set `CWE2E_FRAPPE_MAJOR` for the version leg). `e2e_pkg` is the runtime-deps-only packaging leg (see the `Clean install smoke` entry below); it is off the `-m e2e` matrix, selected only by `e2e.yml`'s dedicated job. A fifth marker, `standalone`, is the ONLY hand-applied one; skill `cwcli-e2e-testing` owns the grouping rule for new E2E tests.
  Unit-tier Typer commands keep their `typer.Option(...)` default objects when a param is omitted, so tests must pass every param explicitly (the `inspect`/`restore` skills flag this trap); the E2E tier instead drives the real `cwcli` binary, exercising Typer parsing. The full E2E protocol + harness contract is in skill `cwcli-e2e-testing`.
  **Test output is deliberately near-silent when green**: one line per test FILE plus one total coverage %, with the failing test's name + traceback only on red (`tests/conftest.py`; contract + rationale in `tests/README.md#reading-the-output`). This REVERSES PR #66's Cockpit/Ledger report, on the captain's own reversal after watching it in real runs - do not reintroduce per-test lines, descriptions, `--durations`, or `--cov-report=term-missing`. Only the fast tier is trimmed; `-v` hands the run back to pytest's stock reporting, which is how the minutes-long E2E tier keeps its liveness. Never set `FORCE_COLOR` to colour a run: it leaks ANSI into the app-under-test's stdout and breaks string-match assertions.
- **CI gates.** `lint.yml` runs black + ruff (scoped to `src/`); `test.yml` runs the `Pytest` (now `-m unit`, the fast tier), `Mypy`, and `Clean install smoke` jobs on pushes and PRs to all branches; `e2e.yml` runs the real-Docker `e2e` matrix (v14/v15/v16) on PRs into `develop`/`master` and on-demand via the `e2e` PR label, but only when the diff actually touches logic/deps: a cheap `changes` job (merge-base diff over `src/**`/`pyproject.toml`/`uv.lock`/`tests/e2e/**`; dispatch/`e2e`-label force it) sets `run=true/false`, and each matrix job gates every Frappe step on `needs.changes.outputs.run == 'true'` - a docs/CI/CHANGELOG/pure-rebase change short-circuits the job to green in seconds. Deliberately NOT a top-level `paths:` filter, which would leave a required context stuck `pending` forever (blocking merge) instead of reporting green.
  Each version leg is split into `shared` and `standalone` jobs.
  The authoritative workflow contract, required-check names, and branch-protection state live in `docs/contributing/ci-cd.md`; skill `cwcli-e2e-testing` owns the test-authoring protocol.
  `Clean install smoke` does a runtime-deps-only `uv tool install .` into an isolated tool dir, asserts the env is runtime-only (`click` present, `pytest` absent), then runs `cwcli --help` / `config --help` / `config edit` / `config path`. Every other job and the local loop use `uv sync --all-extras`, where transitive/dev deps mask an undeclared runtime import - exactly how cwcli once shipped broken (`commands/config.py` imported `click` without declaring it; typer 0.27 stopped supplying it transitively). Any command a user imports MUST be covered by a declared `[project.dependencies]` entry, and this job is the guard over `--help`/`config` reads; `e2e.yml`'s `E2E (runtime-only install)` job is the same runtime-deps-only install driven through a full real-Docker lifecycle instead (the `e2e_pkg` marker), catching a dep imported lazily inside a command body that this job's shallow reads would miss.
  `test.yml` also runs `Pytest (Windows, auto-inspect)` on `windows-latest` - the ONLY non-Linux runner, deliberately narrow to `tests/test_auto_inspect.py`. It exists because a Windows-only defect in `utils/auto_inspect.py` survived precisely because everything ran `ubuntu-latest`, and the repo is public so Windows minutes are free. Platform-dependent process/path/signal work belongs in that suite, not assumed covered by the Linux jobs; widening it to the full `unit` tier is unproven and tracked separately. See `docs/testing/guide.md#the-windows-job-why-it-exists-and-why-it-is-narrow`.
- **Release.** See skill: `cwcli-release`.
- **Suggested commands.** Any `bench`/`docker exec` command cwcli SUGGESTS to a user (hint, error, success message, help text) must be phrased as the `cwcli run <project> [--site <site>] <bench-args>` wrapper or the appropriate cwcli verb (`cwcli apps install`, ...), never a raw in-container command the user cannot run.
  Substitute the live project/site/flag values at the point the hint is printed so it is copy-paste accurate against `commands/run.py`'s pass-through signature.
  A suggested bench command that prompts must carry `-i` (`cwcli run <project> -i new-app <app>`); README.md's `run` section owns the user-facing behavior.
  This is only for SUGGESTIONS; cwcli's own internal `bench`/`docker exec` construction it executes stays as is.
- **Commits.** Author commits as `karotkriss <mckay.christopher73@outlook.com>` only.
  Never add an agent name as a co-author.
  Never hand-edit `CHANGELOG.md` outside a deliberate version bump, and never edit auto-generated files.

## Captain standards (cross-cutting, apply to ALL cwcli work)

These are load-bearing and apply regardless of which command you touch; they stay in this always-loaded core, never buried in a per-command skill.

- **Support AND test BOTH interactive and non-interactive modes for every prompting command.**
  Interactive (a human at a TTY): every prompt is shown AND genuinely collects input - a prompt that is skipped, or returns empty without waiting, is a bug (e.g. the restore MariaDB credential prompts skipping after the "are you sure?" confirm).
  Non-interactive (an agent/automation, or any non-TTY): every prompt has a flag (`--yes`/`-y` for confirmations, `--mariadb-root-username`/`--mariadb-root-password` for credentials, `--site` and the backup selectors, ...) so the command runs to completion with NO prompt; a non-TTY WITHOUT the needed flag must refuse with a non-zero exit, never silently proceed, default, or hang.
  This is both an AXI requirement (agents drive cwcli non-interactively) and a UX requirement, and it must be E2E-verified in BOTH modes on a real instance (drive the TTY via a pty, awaiting prompt_toolkit's `ESC[?2004h` raw-mode marker before each keystroke). Full protocol: skill `cwcli-e2e-testing`.

- **Real-instance validation is CI's job. The local validation gate runs the fast `unit` tier and provisions NOTHING.**
  The reason the real-instance E2E matters is unchanged and still load-bearing: unit-green is not proof for a behavior change, and review fixes make it worse, because the review/document steps and post-run review suggestions frequently produce behavior-altering fixes that land AFTER the author's own E2E ran (e.g. `start` skip-and-continue vs abort, `label --clear` DB/marker consistency, `inspect` Tier-2 read-only, restore path/prompt changes) - so the code that ships is not the code the author validated.
  CI is what closes that gap, and it closes it better than a local re-run can: [`.github/workflows/e2e.yml`](.github/workflows/e2e.yml) runs the real-Docker v14/v15/v16 matrix plus the runtime-only leg against the FINAL pushed code, re-runs on every fix commit, covers three Frappe majors instead of one, and blocks the merge.
  A local re-run duplicates that at minutes per bench build and proves less, so the gate must not do it: `commands.test` in [`.no-mistakes.yaml`](.no-mistakes.yaml) pins it to `uv run pytest -m unit`, matching [`docs/testing/guide.md#gate-policy`](docs/testing/guide.md#gate-policy).
  This scopes every real-instance requirement in this section - the both-modes rule above and the dangerous-delete lifecycle below included: discharge them with a COMMITTED E2E test that CI runs, plus, while you are developing a change whose behavior you cannot otherwise observe, ONE throwaway instance in your own loop BEFORE validation.
  Committing the test is what makes the requirement real; a requirement whose only proof is a local run nobody repeats is covered nowhere.

- **Validate dangerous-delete work with a real full lifecycle, against the editable install, never mocks/PyPI.**
  Any change to a destructive-delete path (`rm` and its backup gates above all) must be proven by a real full lifecycle on a throwaway, isolated instance: real `cwcli init` -> seed real data -> `rm` with backup, then verify the backup is genuinely present/restorable and the deletion is honest (volumes + dir actually gone).
  Run it against the worktree's OWN editable install (`uv run cwcli` / a `uv tool install` from the worktree), never mocked fakes and never a PyPI-published build - the point is to exercise the exact code under review, not a stand-in.
