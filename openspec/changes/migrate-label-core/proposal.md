## Why

Every bench-scoped `cwcli axi` verb takes `--bench <index|label>`, and an ambiguous multi-bench project is a usage error telling the agent to pass one.
**No axi verb tells an agent what the valid values ARE.**
Verified against every core DTO that could carry them: `core/list.py:22`'s `InstanceDTO` is `{project_name, status, ports}` and holds no bench data, and `core/where.py:22`'s `WhereMatch` carries a `bench` path only as a by-product of an apps/sites search you must already know a name to run.
So an agent that runs `cwcli axi backup proj` and gets back `error: multiple benches; pass --bench <index|label>` (`commands/axi.py:79`) has no structured way to discover the answer, and must fall back to the human `cwcli inspect`.
That is a dead end on the agent surface, and `label` is the command that owns bench listing (`commands/label.py:69-71`).
Migrating it closes the dead end with `cwcli axi benches <project>`.

`label` is also the cheapest possible second data point for a foundation branch that shipped on spec and has never run in production.
`resolvers.resolve_container_state`'s `offer_choice=False` branch (`core/resolvers.py:84-89`) raises `CwcliError(NOT_RUNNING)` for a caller that wants "must be running, do not auto-start".
Its only exercise today is `tests/test_core_resolvers.py:59`; the three production callers (`core/backup.py:54`, `core/unlock.py:75`, `commands/utils.py:66`) all pass `offer_choice=True`.
`label` is exactly the caller that branch was built for: `commands/label.py:100-110` deliberately refuses to auto-start, because a label change should not spin up a stopped project.
So this batch does not merely avoid needing a new primitive; it retires a piece of speculative scaffolding into a real consumer, and it is the evidence the branch was specified right.

`label` is the last of the thin remainder, and the batch is one command rather than the three originally scoped, on evidence gathered by reading the code:

- **`run` is CUT.** It is not thin-but-innocent: its terminal operation (`commands/run.py:69`, `api.exec_start(exec_id, stream=True)`) IS the streaming machinery the rework defers, shared verbatim with two deferred commands. `commands/apps.py:65`'s own docstring says the block "Mirrors ``run.py``". The full `stream=True` inventory in `src/` is `run.py:69`, `apps.py:70`, `update.py:37`, `init.py:171`, and the last three are all deferred. Buffering it the way batch 1 buffered `unlock` does not transfer: `unlock`'s payload is a locks directory gone in milliseconds, while `run`'s is arbitrary (`bench migrate` is the first documented example at `README.md:1327`, `bench build` takes minutes) and `commands/update.py:39`, the same stream, carries the comment "Write directly to stdout to preserve carriage returns and progress bars". `run` is re-homed as the reference slice of the streaming batch, where it is the contract's simplest consumer rather than its least representative shaper.
- **`self_update` is CUT because it is already migrated.** `core/version.py` has been UI-pure since its first commit and returns `Result[VersionInfo]` (`core/version.py:56`); `commands/self_update.py:54` is already the thin frontend, and says so in its own module docstring. There is no migration to perform.

A one-command batch is worth its PR: it closes the agent-surface dead end, retires the `offer_choice=False` scaffolding into a real caller, and is deliberately boring, which is this batch's stated purpose before the batches that must add machinery.
Padding it with `run` would do the opposite of that purpose.

## What Changes

- **`core.label`, split into a read and two mutations rather than one mode-switching function.** Add `core.list_benches(project) -> Result[BenchList]`, `core.set_label(project, *, bench=None, label) -> Result[LabelOutcome]`, and `core.clear_label(project, *, bench=None) -> Result[LabelOutcome]` in a new `core/label.py`. Today's `label` is two operations wearing one command: `commands/label.py:69-71` takes a missing selector as a legitimate read request, NOT as an ambiguity, so list mode is not a `NEEDS_CHOICE` fork and must not be modeled as one. Set and clear are two functions rather than one `label=None`-means-clear function, because that sentinel is exactly what batch 1 retired from `_stop_project`; `db_utils.set_bench_label` keeps its `None`-clears convention at the DB layer, and the core does not propagate it into its public API.
- **Zero new primitives, with ONE disclosed widening.** `core.label` is built from `core_docker.get_frappe_container`, `resolvers.resolve_container_state(offer_choice=False)`, `resolvers.resolve_bench`, `bench_labels` (already UI-pure), `db_utils.set_bench_label`, and the envelope. Nothing new is invented. But `resolvers.py:88` hardcodes `hint="Pass --yes to auto-start it, or start it first with 'cwcli start {project}'."`, and `label` has no `--yes` and never will, so the hint becomes a caller-supplied parameter defaulting to today's string. That is a string-parameterization, not a structural bend, and it is reported rather than absorbed because it is a real instance of a shipped primitive carrying an assumption baked in by its first callers, caught exactly where batch 1's falsifiable claim was designed to catch it.
- **`resolvers.cached_benches(project)` extracted, and the reason is a layering fact, not a line count.** `(cached_data or {}).get("bench_instances") or []` is written out four times: `core/resolvers.py:128`, `commands/utils.py:272`, `commands/label.py:59`, and `commands/label.py:150`. One of the four is already a named private helper, `commands/utils.py:269`'s `_cached_benches`. The core duplicates it because `core/` must never import `commands/` (verified: no such import exists, and the dependency direction is the whole point of the layer). So this is not a fresh abstraction being invented at the fourth caller; it is an existing helper sitting one layer too high, moved down into `core/resolvers.py` where both layers can reach it, with `commands/utils.py:183,211` re-pointed at it. This is extraction of duplicated code, which batch 1's Decision 1 explicitly rules does NOT count against the zero-new-primitives claim.
- **Reseated thin `commands/label.py`.** `_print_bench_list`, the `rich` markup, the "Available benches" list rendered on a bad selector, and the exit codes all stay in the frontend. Flags, messages, and exit codes are preserved.
- **Two axi verbs, not one mode-switching verb.** `cwcli axi benches <project>` is the discovery verb; `cwcli axi label <project> [--bench <sel>] --set <label> | --clear` is the mutation. Mode-switching a single verb on whether `argv[2]` exists is the wrong shape for an agent surface and the axi guidelines disfavor it. Both are thin `emit_result`/`exit_for` calls on the established pattern.
- **`cwcli axi self-update --check`, the READ half only.** `core.version.check` already returns `Result[VersionInfo]` and `VersionInfo` is already a serializable frozen dataclass (`core/version.py:36-53`), so the verb is ~20 lines on the existing helpers with no core work. The MUTATING `cwcli axi self-update` stays deferred: nobody recorded why it was deferred originally, the read half is free, and the mutating half (an agent upgrading the tool it is executing from, mid-session) is the part that plausibly had a real reason. A decision whose rationale is lost is not overridden here. One decision this does force: **the axi verb exits 0 when an update is available, deliberately diverging from `cwcli self-update --check`'s exit 1** (see design Decision 5).
- **A NON-INTERACTIVE `label` E2E. ONE mode, deliberately.** `label` does not prompt: there is no `questionary`, no `isatty`, and no `confirm` in `commands/label.py`, and it does not call `ensure_containers_running` because it refuses to auto-start. So the captain's both-modes standard, whose trigger is a prompt, does not bite, and performing a both-modes ritual with no prompt to drive would be theatre. It gets one non-interactive E2E anyway, because it is a mutation with a documented two-store consistency hazard that CLAUDE.md's own captain standard cites by name ("`label --clear` DB/marker consistency"), and a two-store property against a real container is precisely what unit fakes cannot prove.
- **Drive-by: the dead `verbose` param, and the dead CLI flag it exposes.** `verbose` is accepted and never read in all three `bench_labels` marker functions (`utils/bench_labels.py:133,168,190`), the same species as batch 1's `2756361`. Removing it exposes a second fact: `commands/label.py:43`'s `--verbose` flag feeds ONLY those dead params (`label.py:118,134`), so `cwcli label --verbose` is provably a no-op today and has been shipping as a flag that does nothing. It is kept and given honest meaning rather than removed (removal would break a CLI surface for no gain); see design Decision 6. `commands/inspect.py:241,610` also pass `verbose` to these functions and are updated, but `inspect`'s own `--verbose` is real and is untouched.
- **NOT BREAKING.** `cwcli label` keeps its arguments, flags, messages, and exit codes. The one behavior nuance is that `--verbose` starts emitting output where it previously emitted none: additive, opt-in, and impossible for an existing caller to regress on.

## Non-Goals

This section is deliberately precise about what remains, because `migrate-unlock-stop-core/proposal.md:56` was not.
Its Non-Goals bullet swept `label`, `run`, and `self_update` into "the monsters ... stay un-migrated", contradicting batch 1's own audit 30 lines earlier in `design.md:24-27`, which correctly recorded `self_update` as already logic-migrated.
That prose list is what scoped this batch wrongly at three commands, and the record is corrected here so the next batch does not inherit the same error.

- **The accurate un-migrated list.** Genuinely un-migrated, each a later change: `inspect` (672 lines), `restore` (2118), `rm` (1628), `apps` (504), `config` (516, a 19-subcommand host-side grab-bag that is mostly not Docker at all and deserves its own batch), `init` (1285), `run` (78, see below), and `open`. `logs` (234) is a PARTIAL: it imports `core.supervision` and `core.resolvers` but has no `core.logs` and no verb. `self_update` is NOT on this list: its logic is migrated and only its mutating verb is deferred.
- **`run` is excluded on structure, and re-homed rather than dropped.** It is the streaming contract's simplest consumer and should be the reference slice of a streaming batch designed against all four consumers (`run`, `apps`, `update`, `logs`), the same role `backup` played for the foundation. Building the iterator here would let its shape be set by an arbitrary-passthrough whose DTO is by definition an opaque text blob plus an exit code, repeating on `run` the exact error batch 1 avoided on `unlock` (`design.md:66`). `run` also has no coherent axi verb: `README.md:839` records that the `apps` group exists specifically to replace "dropping to the raw `cwcli run <project> bench get-app ...` escape hatch", so giving `run` an axi verb would re-open the escape hatch `apps` was built to close. **Inherited precondition for that batch:** `run` is a prompting command (`run.py:39` auto-start confirm, gated by `--yes` at `run.py:30-32`) with NO E2E today. Standing policy already requires it in both modes, so the streaming batch inherits that gap as a known precondition rather than rediscovering it.
- **The mutating `cwcli axi self-update`.** Deferred, deliberately and on the captain's ruling. Only `--check` ships.
- **`open`.** Still excluded on batch 1's Decision 4 grounds, unchanged: `exec_into_container` (`open.py:359`) uses `os.execvp()` to replace the process and never returns, so it cannot return an envelope; there is no serializable axi verb; and it depends on the un-migrated `inspect`. It needs its own design answer for how a process-handover command relates to a return-a-DTO core.
- **Streaming event-iterator machinery.** Deferred to the streaming batch. `label` needs none: its marker I/O is one `exec_run` each (`bench_labels.py:184,197`), the same shape as `core/unlock.py:117,133`.
- **A plan/apply split.** A label is a reversible string in two stores; there is no preview boundary to draw. Plan/apply arrives with `restore`/`rm`.
- **The AXI cross-cutting shell.** The SessionStart hook, the installable skill, `skills-lock.json`, and the content-first home refinements remain the narrowed `cwcli-axi-pass-x9`. This change adds three verbs on the existing surface.
- **The set-path DB-write asymmetry is PRESERVED, not fixed.** `commands/label.py:142` ignores `db_utils.set_bench_label`'s return value on the set path, while the clear path checks it at `:125`. This is asymmetric but defensible, and the migration preserves it verbatim rather than tidying it into symmetry (see design Decision 4). Changing it is a behavior change that does not belong in a migration whose contract is "not breaking".
- **`bench_labels`'s own module structure.** It is already UI-pure and correctly shaped; it is reused as-is and only loses a dead parameter. It is NOT moved into `core/`.
