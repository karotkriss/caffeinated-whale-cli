## Why

**`cwcli run <project> migrate` can report SUCCESS on a bench command that never finished, and `cwcli apps uninstall` can report a successful uninstall on one that never happened.**
Both were reproduced first-hand against this worktree, not inferred:

```
run.py:78-79   exit_code = result.get("ExitCode", 1)   # ExitCode is None -> None
               raise typer.Exit(code=exit_code)        # -> process exit 0.  VERIFIED
apps.py:78     return result.get("ExitCode", 1) or 0   # None or 0 -> 0.     VERIFIED
```

Docker's `exec_inspect` returns `{"ExitCode": None, "Running": True}` while an exec is still going, so the key is **present** and `dict.get("ExitCode", 1)`'s fallback of `1` is dead code that never fires.
`None` then flows straight to success: `typer.Exit(code=None)` exits **0** (run), and `None or 0` is **0** (apps).

This is not theoretical. `CancellableStream.__next__` (`docker/types/daemon.py:28-33`) swallows `urllib3.exceptions.ProtocolError` and `OSError` into `StopIteration`, so **a dropped Docker connection is indistinguishable from a clean end of stream**.
The loop ends, `exec_inspect` reports `ExitCode: None`, and `cwcli apps uninstall <proj> --app X` reports `"ok": True` for a destructive uninstall that may not have run.

This is the same disease as the `UnicodeDecodeError` crash that shipped today (`cwcli-exec-decode-crash-d5`, PR #79) - the tool says "fine" when it is not - except **silent**.
Getting it right means polling the exit code, which is the streaming primitive's job.
That is why this batch carries the fix rather than splitting it out: unlike the decoder, it has no clean standalone shape.

**The decode argument for this batch is dead, and this proposal does not make it.**
PR #79 consolidated all four exec sites onto one shared `decode_exec_stream` helper (verified on `d6d2349`: `run.py:73`, `apps.py:74`, `update.py:42`).
There is no decoder duplication left to collapse.
What survives PR #79 and still needs this contract:

- **the fail-open exit code** (above), live in two commands, one of them destructive;
- **the leaked stream.** `exec_start(stream=True)` returns a `CancellableStream` wrapping a live socket and HTTP response, and docker-py's own docstring states the rule: "If stream=True, then a generator is returned instead and **the caller is responsible for closing the response**" (`docker/api/client.py:_read_from_socket`). Not one of the four consumers calls `.close()`;
- **the stream tag.** `init.py:171` is the only `demux=True` in the codebase and routes container stderr to `sys.stderr`. Any contract without a per-chunk stream tag silently loses that routing when `init` migrates, and stdout purity is the axi surface's first rule;
- **`run` is the only genuinely untested command left in cwcli** (`tests/README.md:164`), and it is this contract's reference slice.

## What Changes

- **`core/exec_stream.py`, the UI-pure per-exec primitive.** `exec_stream(container_id, cmd, *, workdir=None, environment=None) -> Iterator[ExecEvent]`, yielding `ExecChunk(stream, text)` per chunk and a terminal `ExecDone(exit_code)`. It owns the honest exit code (polled, bounded, never `None` coerced to 0), the stream tag, the incremental decode, and closing the `CancellableStream`. It is a **primitive, not a verb**: `run` is the only consumer with one exec per resolve, while `update` has 13 and `init` has 11 downstream of a single resolve, so a verb-shaped `core.run(...) -> Iterator[RunEvent]` would be unusable by the consumers that matter most (design Decision 1).
- **`core.run_plan(project, args, *, bench=None, bench_path=None, auto_start=False) -> Result[RunPlan]`, the resolve phase.** Two-phase **because generators are lazy**, not because of plan/apply: a generator body does not execute until first iteration, so a core function returning `Iterator[...]` cannot raise `CwcliError` at call time and cannot return `NEEDS_CHOICE` at all (design Decision 2). Phase 1 is an ordinary `Result[T]` on the existing envelope, resolvers, and error taxonomy.
- **`RunPlan` carries `container_id: str`, never a live container.** This is locked decision 4 applied at the phase seam, and it is the decision that keeps the two-phase split honest rather than a loophole (design Decision 3). Accepting a live container as a *parameter* stays fine and is already shipped precedent (`resolvers.resolve_container_state`, `resolvers.require_bench_dir`); the ban is on live objects crossing a `core.<verb>` **return** boundary, which is exactly what a plan does.
- **`exec_stream` always demuxes; there is no `demux` parameter.** Every chunk carries `stream: "stdout" | "stderr"`, and consumers that want today's combined stream write both tags to stdout in yield order. Verified equivalent, not assumed: `demux=True` and `demux=False` iterate the SAME `frames_iter(socket, tty)` in the same order and differ only in the per-frame wrapper (`docker/api/client.py:_read_from_socket`), so the combined byte stream is reproduced exactly (design Decision 4).
- **`decode_exec_stream` is SUPERSEDED and deleted; `utf8_stream_decoder` is reused and stays put.** This answers the brief's question about the relationship between the primitive and the helper PR #79 shipped, and the answer was not visible before this audit: `decode_exec_stream`'s only three callers are `run.py:73`, `apps.py:74`, and `update.py:42` - **exactly the three sites this batch re-points** - so it drops to zero callers and becomes dead code. `utf8_stream_decoder` (the real primitive: one incremental decoder per stream) survives with two consumers, `core/exec_stream.py` and `init.py`, and is NOT moved into `core/` (design Decision 5).
- **Reseated thin `commands/run.py`.** Typer signature, the `--yes`/auto-start prompt via the existing `ensure_containers_running` prologue, rendering, and the exit code stay in the frontend. Flags, messages, and behavior are preserved, with ONE deliberate exception: **`cwcli run` stops exiting 0 on an unknown exit code**, which is the bug this batch exists to fix.
- **`apps` and `update` exec sites re-pointed at the primitive. The commands are NOT migrated.** Required by the captain's ruling, because that is where the fail-open lives. `apps.py:_stream_bench` and `update.py:_stream_command`'s verbose branch become calls into `exec_stream` plus a consumption mode; `_stream_command`'s verbose/non-verbose fork collapses, because the fork was never an exec-layer concern. `apps`/`update` keep their typer signatures, `rich` rendering, fan-out logic, maintenance-mode safety, and exit-code aggregation, and stay on the un-migrated list with no `core.apps`, no `core.update`, and no new axi verb.
- **`run` gets BOTH core unit tests and a both-modes E2E** (captain's ruling 2), not the E2E alone. Every migrated command in batches 1 and 2 shipped core unit tests against faked I/O, and this batch makes the least-tested command in cwcli prove new machinery. `run`'s one existing test (`test_run_streams_split_character_intact`) came incidentally from PR #79 and covers the decode path, not the command.
- **NO `axi run` verb, deliberately.** This batch ships no new axi verb, which breaks every prior batch's rhythm and is stated here rather than discovered in review (design Decision 6).
- **Docs:** `README.md:1330`'s documented `cwcli run frappe-one --site development.localhost migrate` example **exits 2 and cannot work** (verified against the real binary); it is corrected, and `run`'s passthrough flag limitation plus the `--` separator are documented.

## Non-Goals

- **`apps` and `update` as COMMAND migrations.** Their exec sites are re-pointed; their commands are not migrated. `update.py` is not a thin wrapper around a stream but a fan-out state machine: per-site maintenance-mode enable that records each site as it goes, migration of only the sites that actually entered maintenance, a `finally` that must always disable maintenance and report any site left stuck, and a seven-way failure aggregation. Migrating that is untangling a state machine, not applying a contract, and 1435 lines of the two together with new machinery would be unreviewable. **Batch 4**, which the contract unblocks: `apps update` is the only `apps` subcommand without `--json`, and `README.md:839` records why ("apps update delegates to the streaming update flow and has no `--json`"). Streaming is precisely what blocks structured output today, so `axi apps update` cannot exist until this lands.
- **`init`.** 1285 lines; the only consumer carrying live secrets in the exec (`init.py:163-167` passes `environment=` so passwords ride as unexpanded `$CWCLI_*`), and re-pointing the one call site that carries live secrets deserves its own review rather than a paragraph at the end of this one. The primitive supports `environment=` so that migration is unblocked. **Correcting the brief on init's own bug:** the brief states `init.py:193` raises `UnboundLocalError` when `stream_output=True`. **It does not.** `raw_output = output if not stream_output else b""` evaluates the condition first, so when streaming it takes the `b""` branch and never references `output` - verified empirically. The real defect is the recon's milder version: the ENOSPC hint (`init.py:195-199`) is **dead whenever streaming**, which is exactly when a long `bench build` would exhaust disk. Latent, real, and still `init`'s batch; the primitive could restore it with a retained tail buffer, which is a behavior improvement and not a migration item.
- **`logs`.** Not an exec-stream consumer at all. It never touches the Docker SDK: all three of its container reads shell out to the `docker` CLI, and `logs.py:228` passes no `stdout=`/`stderr=`, so the child inherits cwcli's terminal and the log bytes never enter the Python process. **There is no stream to wrap.** `--follow` is a process handover, structurally next to `open`, and belongs with that design question. This also corrects the rework's original prose: `migrate-unlock-stop-core/proposal.md:54` defers streaming "to `logs`/`update`", and of those two names only `update` is right. The real consumers are `run`, `apps`, `update`, `init`.
- **`axi run`.** No DTO to serialize (arbitrary bench stdout is an opaque text blob; `emit_result` is `toon.encode(asdict(data))`); it re-opens the escape hatch `apps` was built to close (`README.md:839`); and the passthrough is broken for the flag-bearing commands an agent would need anyway (design Decision 6). A verb-less core function is established: `core/supervision.py` has no verb, and `core/version.py` shipped verb-less for two batches.
- **A plan/apply split.** The resolve/stream split is about generator laziness, not preview semantics. Plan/apply exists to preview a **destructive** action for confirmation and arrives with `restore`/`rm`. `run` is not destructive. Same two-call shape, unrelated motivation; conflating them would let a later agent think this batch settled the plan/apply question. It does not.
- **`run`'s argv passthrough.** `run` cannot pass through any bench flag, because typer claims the argv first (verified: `--site` exits 2, `--branch` exits 2 with click helpfully suggesting `--bench`, cwcli's *bench selector*, for what the user meant as a *git branch*). This is a **frontend** defect that the migration does not touch, which is why the doc fix is in scope and a signature change is not. Fixing it properly means `typer.Context(allow_extra_args, ignore_unknown_options)` or making `--` mandatory, both of which are CLI-surface changes deserving their own item.
- **The accurate un-migrated list.** After this batch: `inspect` (672), `restore` (2118), `rm` (1628), `apps` (505), `config` (516), `init` (1292), and `open`. `logs` (234) stays a partial. `self_update` is NOT on this list (logic migrated; only its mutating verb is deferred). `run` leaves it.
- **The AXI cross-cutting shell.** Still `cwcli-axi-pass-x9`.
