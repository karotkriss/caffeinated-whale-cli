## Why

`restore` is batch 11: the MOST destructive path in the codebase (`restore --receive` downloads a peer's backup over sendme and runs `bench restore --force`, which drops and recreates a live site's database), and one of the two commands the core-rework plan explicitly earmarked for the **destructive-preview (plan/apply) boundary** it deferred (`add-exec-stream-contract`'s batch-3 note: "Plan/apply previews a DESTRUCTIVE action for confirmation and arrives with `restore`/`rm`").
Three costs of its un-migrated state, all measured at current HEAD (`commands/restore.py`, 2101 lines, three modes):

**1. The whole destructive core is welded to `rich`/`questionary`/`typer`.**
The `bench restore --force` exec, the encryption-key merge, the migrate + restart, the missing-apps check, and the backup scan all live inline in the Typer command, interleaved with `console.print`, `questionary.confirm`, `TipSpinner`, and `typer.Exit`.
No other frontend (`cwcli axi`, a future GUI) can drive the most safety-critical operation cwcli has; every decision (which backup, proceed-despite-missing-apps, the destructive confirm) is a raw prompt, not a typed choice a non-CLI surface can resolve.

**2. The three modes each re-implement bench-path resolution and the no-cache fallback.**
`restore_send_mode` (`restore.py:705-756`), `restore_receive_mode` (`restore.py:976-1027`), and the normal path (`restore.py:1645-1696`) each carry a byte-for-byte copy of "cached bench? resolve; else run `core.inspect` to populate, re-resolve, else default `/workspace/frappe-bench`" - the fallback-populate pattern `core.open_plan` already owns as one core call.

**3. The destructive gates are correct but frontend-only.**
The destructive confirm on BOTH paths, the missing-apps gate, the non-interactive selectors, secrets-off-the-argv (M5), and the streamed tar copies (M4) are each real shipped safety fixes (issues #40/#41, the receive-mode data-safety pass) - but a core that serves `axi` and a GUI cannot enforce any of them, because they are `sys.stdin.isatty()` branches and `questionary` prompts, not core parameters.

## What Changes

- **`core/restore.py`, a plan/apply split** - the batch's first-class structural finding, disclosed up front (design Decision 1):
  `core.restore_plan(project_name, *, site=None, latest=False, backup_file=None, selected_backup=None, bench=None, bench_path=None, on_event=None) -> Result[RestorePlan]` (the read-only resolve: container/bench/site with the no-cache inspect fallback, scan all backups, apply the `--latest`/`--backup-file`/menu selection, check missing apps, compute the origin mismatch) and
  `core.restore_apply(plan, *, mariadb_root_username, mariadb_root_password, admin_password=None, consent=False, no_migrate=False, on_event=None) -> Result[RestoreReport]` (the destructive act: verify the dump, build the restore command with secrets in `environment=`, run `bench restore --force`, merge the encryption key, migrate, restart).
  This IS the plan/apply boundary the rework deferred here, and the justification is specific: it is a **read/destroy safety separation**, not merely efficiency. `restore_plan` is a pure preview (no secrets, safe to call repeatedly, the natural home of a future read-only "what would restore do"); `restore_apply` is the single guarded destructive act that takes the secrets and the consent. Neither prior two-call motivation applies (no generator laziness - nothing returns an iterator; this is not `run`'s shape), and the destructive CONSENT stays a core parameter (`restore_apply(consent=False)` returns `NEEDS_CHOICE`/`confirm_restore`), the `apps uninstall`/`config cache clear` lesson: consent must never be a frontend-only decision an agent or GUI can bypass.
- **Two new `Choice.kind` tokens, no new primitives**: `select_backup` (the core cannot pick a backup without a selector; `restore_plan` returns it carrying the target/other candidate sets for the menu, the `select_bench`/`select_editor` precedent) and `confirm_restore` (the destructive consent, the `confirm_uninstall`/`confirm_clear`/`confirm_reuse_bench` precedent).
- **The destructive execs stay BUFFERED `exec_run`, not the exec-stream contract** - restore is a `backup`-shaped verb, not an `init`-shaped one. `bench restore --force` and `bench migrate` block to completion and return real exit codes today (`restore.py:1999`, `:2208`); a buffered `exec_run` already has an honest code, so the contract's polling machinery buys nothing here. Secrets ride `exec_run(..., environment=restore_env)` byte-exactly as today (M5), referenced in the command string only as `"$CWCLI_MARIADB_ROOT_PASSWORD"` / `"$CWCLI_ADMIN_PASSWORD"`. `RestoreReport` has NO password field.
- **The streamed tar copies (M4) move to the core**: the receive-path copy-INTO-container (`put_archive`, streamed, checked bool return) and the send-path copy-OUT-of-container (`get_archive` + tar extract) become core helpers. The sendme SEND/RECEIVE subprocess itself, the ticket prompt, the clipboard, and the Ctrl-C wait stay in `commands/restore.py` as a deliberate, disclosed non-consumption (the `commands/logs.py` `-it tail` precedent: interactive host I/O the core does not own), because they are prompts and an interactive wait, not container logic.
- **The three modes' bench resolution collapses to ONE shared frontend PROLOGUE helper** (`_resolve_bench_prologue`: `resolve_bench_path` -> the no-cache inspect fallback -> re-resolve -> `DEFAULT_BENCH_PATH`), the `cwcli backup` prologue precedent - because today all three paths resolve container + bench + site BEFORE the scan/download and byte-exact ordering requires it (design Decision 7). The core keeps backup-style belt-and-suspenders resolution over concrete inputs.
- **restore keeps its OWN default-site resolution, the batch's one reported flat spot** (design Decision 8): `restore.py:_resolve_default_site` adds a LIVE `sites/currentsite.txt` read as a final fallback beyond `resolvers.resolve_default_site` (which only reads the cache and raises), because the destructive path must resolve the default even against a cold/stale cache. Widening the shared resolver would change `backup`/`unlock`; restore keeps its stricter helper private to `core/restore.py`, reported rather than absorbed.
- **`commands/restore.py` thins to a renderer**: the questionary backup menu (rendered from `select_backup`, plus the frontend-only "Restore from remote source" affordance that diverts to receive), the two confirms (rendered from the plan facts, `--yes`/non-TTY-gated exactly as today, both keeping `auto_enter=False`), the MariaDB credential prompts (`_prompt_mariadb_credentials`, unchanged, fired AFTER the confirms), the spinners driven by typed plan events, and the sendme send/receive orchestration.
- **There is deliberately NO `axi restore` verb, and the absence is asserted** (design Decision 9): a `bench restore --force` that drops a live site's database is destructive-action territory of the `axi apps install`/`uninstall` (captain-locked) and `axi init` (captain-deferred) class - a product decision the captain owns on its own evidence, not a rider on the migration. The plan/apply shape makes the verb thin whenever it is decided (`axi restore <project> --latest --yes --mariadb-root-password ...`), so the assertion's docstring records DEFERRED, not a structural refusal; a test pins the registry absence so "deferred" can never read as "forgotten."

## Impact

- **New:** `src/caffeinated_whale_cli/core/restore.py`, `tests/test_core_restore.py`, the no-`axi restore` assertion (in `tests/test_axi.py` or a new `tests/test_axi_restore.py`), `tests/test_restore_characterization.py` (committed green against unmigrated HEAD first, batch 4's discipline).
- **Changed:** `commands/restore.py` (renderer), the two existing restore suites (`test_restore_safety.py`, `test_restore_inspect_fixes.py` - pure helpers re-point with their subject; the receive/normal Typer-command tests split by design into core tests and frontend-render tests, each named in tasks), CLAUDE.md ledger, `cwcli-lifecycle` (`references/restore.md`) + `cwcli-core-axi` skills, `docs/technical/README.md` module list, `tests/README.md` coverage map.
- **Unchanged:** every user-visible behavior (the destructive confirm on both paths, non-interactive selectors, secrets off the argv, streamed copies, post-restore migrate + restart, the encryption-key merge, exit codes, the `--send`/`--receive`/`--latest`/`--backup-file`/`--yes`/`--no-migrate`/`--no-recache` flags), `core/exec_stream.py` (not consumed), the cache schema, `skills/cwcli/SKILL.md` (no verb change, no regeneration).
- **Zero new primitives, as a falsifiable claim**: `get_frappe_container`, `resolve_container_state` (both `offer_choice` modes), `resolve_bench` + `DEFAULT_BENCH_PATH`, `core.start(restart=True)` (the post-restore restart, the `_start_project` -> `core.start` precedent), the envelope, and the `OnEvent` idiom cover every need (the no-cache inspect fallback stays a frontend prologue helper, per Decision 7); `select_backup` and `confirm_restore` are new tokens in `Choice.kind`'s open set, not primitive changes.
  Two items are REPORTED rather than absorbed (design Decision 8/10): (1) restore keeps its own live-fallback default-site resolver, stricter than the shared one; (2) `--receive` has no `--ticket` flag, so it cannot run fully non-interactively today - a PRE-EXISTING gap in the captain both-modes standard that this migration preserves byte-exactly rather than fixing (adding the flag is a behavior addition deferred to its own change, Non-Goals).
