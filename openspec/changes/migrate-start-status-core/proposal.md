## Why

`cwcli start` and `cwcli status` are the last un-migrated lifecycle commands, and today they are both broken in ways the core rework is meant to fix (recon `data/cwcli-startstatus-recon-h9/report.md`).
`start` is fire-and-forget: it shoves `bench start` into the container with `docker exec -d` + `nohup`, keeps NO handle (no PID, no manifest), captures everything into one ephemeral `/tmp/bench-<project>.log`, and "cleans up" with `pkill -f 'bench start'` - which never matches, because bench `os.execv`s into `honcho`, so the running cmdline is `honcho start ...` (§2, §3).
The concrete latent defect: re-running `start` does NOT kill the old stack, so it likely spawns a SECOND honcho - duplicate workers, in-container port clashes (§3, D4).
`status` is a single blind `curl localhost:8000` collapsed to three flat tokens (`offline`/`online`/`running`); it knows nothing about socketio, workers, schedule, watch, or redis, so a dead worker still reports `running` (§1b).
Neither is on the core: both are old-style docker-py + subprocess + `rich`, welded.

This change migrates BOTH onto the UI-pure logic core, TOGETHER, behind one shared tracked-state contract - because the moment `status` reports per-process health it must read exactly what `start` produced (the process set, the supervisor identity, the log path), so they are one unit, not two independent verbs (§6).
It lands under the green net from `add-start-status-e2e-net` (PR 1), which pins the preserved invariants; this change adds its own tests for the new behavior on top.

The settled design (D1-D6, locked with the captain) is: **observe, keep honcho** - `start` keeps launching bench's own honcho and cwcli owns only the READ side; no in-container supervisor, no cwcli daemon.

## What Changes

- **`start` becomes idempotent, on the core.** Add `core.start(project, *, bench=None, bench_path=None, auto_start=False, ...) -> Result[StartOutcome]` owning container start + bench resolution + the `bench start` launch. Detect an already-running bench by DISCOVERED supervisor PID keyed to the resolved bench path (NOT `pkill -f 'bench start'`), and if it is already running, no-op and return an `already_running` outcome with a status line ("already running: N/N processes up"), exit 0. This fixes the double-start bug (D4). `start` is non-destructive; no plan/apply split.
- **`status` reports real per-process health, one-shot, on the core.** Add `core.status(project, *, bench=None, bench_path=None) -> Result[StatusReport]` that replaces the blind `curl` with real health from ONE cheap `ps` in the container: per-process up/down, uptime, CPU%, RSS, mapping PIDs to Procfile labels (web, socketio, worker[/queue], schedule, watch, redis) via their self-describing cmdlines. Keep the web HTTP code as one field. Emit a pre-computed `overall` aggregate (`offline`/`online`/`running`/`degraded`), distinguishing "containers up but supervisor down" (a start marker exists, honcho does not) from "bench never started" (no marker). One-shot snapshot only.
- **One shared tracked-state contract + read-side discovery substrate.** Introduce the shared substrate both verbs use: the per-process discovery (one `ps` -> label-mapped `ProcessHealth` set), the live Procfile parse for expected labels, and a minimal supervisor marker `core.start` writes on launch (`{supervisor, started_at, log_path}`, on the workspace volume so it survives container restart) and `core.status` reads. The diff of (marker says started) x (Procfile expected) x (live `ps`) is the honest `overall`. `start` and `status` share ONE bench selector (`resolvers.resolve_bench`) so they always agree on which bench they report (§6).
- **Multi-bench aligns to the family (D5).** Drop `start`'s lenient `on_ambiguous="first"` + note. On a multi-bench project with no selector, the interactive `cwcli start`/`cwcli status` prompt which bench (via the existing `select_bench` needs-choice + CLI wrapper), and `cwcli axi start`/`status` take `--bench` or return a `select_bench` usage error - exactly like `backup`/`inspect`. Single-bench is unaffected (no prompt). The post-restore restart keeps passing an explicit `bench_path` (restart the SAME bench it migrated), preserved via `core.start`'s `bench_path` param.
- **Logs persist and are bounded (D2).** Move the captured honcho stream off ephemeral `/tmp` into the bench's own `logs/` dir (`{bench_path}/logs/bench-start.log`, on the frappe_docker workspace volume, so it survives container restart), with a simple size cap so it cannot grow unbounded (truncate-on-(re)launch to bound across restarts, plus a fixed byte cap during a run; no new image dependency, no cwcli daemon). Per-process log views are recovered by parsing honcho's built-in `HH:MM:SS name|` line prefix - no extra plumbing.
- **`cwcli logs` follows the new location (IN SCOPE, must not break).** Update `commands/logs.py` (which hardcodes `/tmp/bench-<project>.log`, duplicated from `start.py`) to resolve the bench-start log path through the shared contract (one source of truth, killing the cross-file duplication), and verify `restart` (which reuses the reseated start) still works.
- **Reseat the CLIs and add the axi verbs.** Reseat interactive `cwcli start` / `cwcli status` as thin frontends over the core (typer signature, the variadic multi-project loop + stdin piping + trailing-flag recovery, `rich` output, spinner, and CLI-side choice resolution stay in the frontend). Add `cwcli axi start <project> [--bench] [--yes]` and `cwcli axi status <project>` on the existing `cwcli axi` serializer/exit-mapper, emitting TOON with the pre-computed `overall` up front and a definitive offline/empty state.
- **Port-conflict logic stays a CLI-frontend host-side pre-step (D6).** `_check_port_conflicts` (host-side, stops other Frappe projects, prompts) keeps its prompting in the frontend, mirroring how `ensure_containers_running` was split; `core.start` assumes ports are already clear (a documented precondition, as `_start_project` already documents today). `cwcli axi start` never prompts: it surfaces an unresolved conflict as a `CONFLICT` structured error and `--yes` auto-resolves conflicting Frappe projects (today's non-interactive branch).
- **BREAKING**: `start` multi-bench no-selector behavior (was `first-with-note`, now prompt/error) and `status` output (was three flat tokens, now a richer report whose primary line is the `overall` aggregate, now able to say `degraded`). Both are deliberate per D5/design point 2; pinned green by PR 1's invariant net and covered by this change's new-behavior tests.

## Capabilities

### New Capabilities

- `bench-process-supervision`: the shared read-side supervision substrate for the lifecycle commands - one cheap `ps`-based per-process discovery in the frappe container that maps PIDs to Procfile labels and yields up/down/uptime/CPU/RSS; the live Procfile parse for expected labels; the minimal supervisor marker `core.start` writes and `core.status` reads (the tracked-state contract that lets status distinguish supervisor-down from never-started); the honcho-prefix log parse for per-process views; and the persisted, size-bounded bench-start log on the workspace volume with `cwcli logs` reading its single-source-of-truth path.
- `start-status-core-slice`: `core.start(...) -> Result[StartOutcome]` (idempotent, discovered-PID double-start guard, no plan/apply) and `core.status(...) -> Result[StatusReport]` (real per-process health, pre-computed `overall`, one-shot), sharing one bench selector; the reseated interactive `cwcli start` / `cwcli status`; and the `cwcli axi start` / `cwcli axi status` verbs - all behind the green start/status E2E net.

### Modified Capabilities

- (none - `openspec/specs/` holds no archived capabilities yet, so no existing requirement changes. The `start`/`status` behavior changes are captured as requirements of the new capabilities above, and the E2E net from `add-start-status-e2e-net` stays green as the preserved-invariant floor.)

## Non-Goals

- **Per-process restart resilience (explicit NON-GOAL).** honcho is all-or-nothing (one process dies, it kills the rest, and it never restarts a crashed process - §2). This change does NOT build anything that restarts individual processes, and does not add an in-container supervisor (supervisord/s6/pm2) or a cwcli daemon. Per-process health here is an honest liveness + resource snapshot of an all-or-nothing stack, not resilience (D1 option 1).
- **The live `status --watch` stream (DEFERRED).** The one-shot snapshot ships here; the live/streaming health surface (a typed event iterator per the core plan's streaming contract) is backlog item `cwcli-status-watch-w7` and is NOT built here (D3).
- **A plan/apply split for `start`.** `start` is non-destructive; making it idempotent is the correctness fix, not a preview boundary (D4).
- **Migrating `logs`/`restart` fully onto the core.** They are updated only as needed to keep working over the relocated log and the reseated start; their own core migration is a later change.
- **The AXI cross-cutting shell** (SessionStart hook, installable skill, `skills-lock.json`) - the narrowed `cwcli-axi-pass-x9`, unchanged by this slice; this change adds only two verbs on the existing `cwcli axi` surface.
