# `scale` command internals (sharp edges)

Each note guards a real, verified finding; keep the root-cause "why" so a later change does not silently re-break a data-safety property. The one-line contract lives in the always-loaded `AGENTS.md` "Important Components"; this is the incident detail. Every claim below was verified against a real instance (`fm/multibench-scale-verify`, the report the feature was built from - read it for the container evidence).

`scale` lives entirely on the logic core: `core/scale.py:scale(project, *, to, consent, on_event) -> Result[ScaleReport]`. `commands/scale.py` (human) and `commands/axi.py:axi_scale` are thin renderers.

## The defect it fixes: silent host-unreachability past six benches

An instance's `conf/docker-compose.yml` publishes a FIXED range - the six web ports `8000-8005` and six socketio ports `9000-9005` cwcli writes at init (`core/init.py:569-573`, string-replacing the upstream template). Per-bench web/socketio ports are NOT assigned by cwcli - they are assigned by **bench init's own `make_ports`** (`bench/config/common_site_config.py`), which scans sibling bench folders in the shared `/workspace` parent and increments from 8000/9000, storing the result in each bench's `sites/common_site_config.json`. The Procfile web line is templated `--port {{ webserver_port }}` from that value, so there is no port clash between benches - but a **7th** bench gets `webserver_port: 8006`, binds `:8006` INSIDE the container fine, and is **silently unreachable from the host**: `docker port <cid> 8006` returns "no public port", no crash, no warning. That silent unreachability is the whole defect.

**cwcli writes ZERO port config today** - grep of `src/` for `webserver_port`/`socketio_port` finds only the cache read (`utils/db_utils.py:145-147`, a DERIVED mirror). So the feature must READ bench's `common_site_config.json` as the source of truth; it must NOT invent a second authoritative port-assignment store that can drift from bench's. `_read_assigned_ports` reads each bench's config live via `cat` inside the container.

## The four invariants (each a real safety property)

1. **Read, don't invent, the port truth.** `_read_assigned_ports` -> `{bench_path: (webserver_port, socketio_port)}`. A bench whose config is unreadable is SKIPPED, not defaulted, so a transient read error never shrinks the reconciliation target. Reconcile target = cover `[8000..max(webserver_port)]` / `[9000..max(socketio_port)]`, honor the optional `--to N` floor, and NEVER go below the current published count: `target = max(published.count, needed, to or 0)`. It only ever EXPANDS, so re-running when the range already covers every bench is a safe idempotent no-op (`expanded=False`, nothing recreated).
   `_parse_published_range` accepts both quoted and unquoted YAML port scalars and `_widen_ports_block` preserves that spelling.
   This is required because fresh init now quotes the mappings it adds to upstream's portless devcontainer template; accepting only the older unquoted spelling made scale reject cwcli's own compose output.

2. **`--no-deps` is MANDATORY.** `_recreate_frappe` applies the widened compose with `docker compose -p {project} -f docker-compose.yml up -d --no-deps frappe` (reuses init's `compose_base` shape). `--no-deps` recreates ONLY the frappe service and leaves MariaDB/Redis + the DB volume untouched - proven DB-safe in the report's H4 (MariaDB container id unchanged, a seeded DB marker read back intact). **NEVER `docker compose down`, never recreate without `--no-deps`** - either takes MariaDB with it and destroys the database. `tests/test_core_scale.py` asserts the recreate command contains `--no-deps`/`up`/`frappe` and does NOT contain `down`; `tests/e2e/test_scale_e2e.py` proves the DB survives on a real instance. This is a NEW capability: `core.start` uses the Docker SDK `container.start()` (`core/start.py:105`), which cannot change a port mapping - only a compose recreate can.

3. **Post-recreation toolchain repair, per bench, by major (the H5 gotcha).** Recreation reverts `/home/frappe` to the image state (it is in the container's writable layer; only `/workspace` is a bind mount and only `mariadb-data` is a volume). For **v13/v14** benches the RUNTIME-installed nvm node + pyenv python are WIPED (a dangling `env/bin/python` is bench-FATAL, worse than the node loss); **v15/v16** node/python are image-baked and survive untouched. `_repair_toolchains` probes each bench's `env/bin/python` (`_python_ok`) and re-runs cwcli's OWN idempotent installers - `_install_pyenv_python` FIRST (bench-fatal if skipped), then `_install_nvm_node` - reusing them from `core/init.py` verbatim, with a `chown_home=True` `align_container_user_to_host` FIRST (once, only when at least one bench needs it) so the installers can write the host-owned home. It only reinstalls a GENUINELY broken interpreter (fail-honest, cheap), reading the bench's major from `apps/frappe/frappe/__init__.py` (not `env/bin/python -c import frappe` - that is what is broken). pyenv reinstall restores the same patch version on the same image, so the venv symlink target reappears and no venv rebuild is needed; if a repair leaves the interpreter still broken it WARNS rather than claiming the bench is fixed (there is a `ponytail:` note on the same-image-resolution assumption). A broken interpreter on an image-baked major is warned, not silently ignored. Old-major repair is unit-tested against the real installer functions (`test_v14_broken_interpreter_reinstalls_pyenv_and_nvm`) because a real v13/v14 bench is impractical on the v16 E2E leg.

4. **Consent is a CORE decision, not frontend-only.** Expanding recreates the frappe container, which restarts EVERY serving bench in the instance (they share one container's supervisord) - unavoidable, the port map is a container-creation property. So `scale(consent=False)` returns `NEEDS_CHOICE` `confirm_scale` when (and only when) expansion is actually needed, rather than letting axi/GUI bypass the warning (the `apps uninstall` fused-consent lesson: consent must not be a frontend-only decision). A no-op needs no consent - nothing restarts. The human frontend renders `confirm_scale` as a confirm honoring `--yes` (refusing a non-TTY without it); `axi scale` renders it as an exit-2 usage error naming `--yes`. After recreation `scale` relaunches supervisord for every bench via `core.start(restart=True)`; a bench that fails to relaunch is a WARNING, not an abort (the others still come up).

## After recreation, the old container handle is dead

`_recreate_frappe` destroys and recreates the frappe container, so the `frappe_container` handle resolved before it points at a gone container. `scale` re-resolves via `core_docker.get_frappe_container` after `_wait_for_frappe_running` and uses the fresh handle for the toolchain repair and the post-expand config re-read. A repair or a port-map read on the stale handle would raise a `docker.errors.NotFound`.

## Honesty: memory, not ports, is the real ceiling

The report measured two full serving benches peaking ~8.4Gi on an 11Gi box. Publishing more ports adds no memory. `scale` emits a `scale.memory_ceiling` warning when it expands past six ports and does not pretend the port count is the binding limit - do not remove that honesty.
